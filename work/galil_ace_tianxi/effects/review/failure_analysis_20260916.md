# 天袭光效失败分析（2026-09-16）

## 结论

当前失败主要发生在效果重建阶段：原始资源已恢复，但构建仅使用了一个原始光效模型和简化的眼部面片，没有实现参考画面中的完整效果组合。与此同时，预览使用了不同的发光/后处理，PCF 不可见也未定位到具体运行时环节。不能把整体差距归结为亮度不足或 Source 1 无法显示 viewmodel 粒子。

本次只读检查源数据、构建脚本、产物和实际 MIGI pak，新增审查报告及 PCF 文本解码副本；未重建、部署、修改游戏或推送。

## 1. 截图能说明什么

- 图 1：当前 CS:GO 画面以普通枪身材质为主，前部有一个较小蓝色光斑；参考图中明显的枪身中部流光、多个发光部件及后部亮核没有表现出来。
- 图 2：CF 参考同时包含前部光团、中段蓝色能量纹路/光带、后部圆形亮核和局部亮色装饰。
- 两图视角、持枪姿态、画面缩放和环境照明不同。可以据此判断大块效果缺失，但不能直接按像素比推算世界尺寸，也不能从两张静帧确认变色周期、粒子生命周期或截图对应的构建版本。

## 2. 已确认：效果覆盖不完整是首要原因

原始 `assets/weapons/galil_ace_tianxi/effects.json` 有 29 个 idle 节点：14 LTBModel、7 ParticleSystem、5 Sprite、3 FlareSpriteFX。

实际构建的 `FX_LAYERS` 仅包含 `PARTS_BLUE`：

- 构建入口：`native_vm/build_galilace_vm.py:84`。
- 光效模型遍历：同文件 `:402`。
- 生成的 SMD 中，新增材质几何只有 `fx_galilace_parts_blue`（34 三角形）、`fx_galilace_eye`（6 三角形）、`fx_galilace_eye_core`（6 三角形）。
- 缺少其余 13 个 LTBModel 节点，包括 L/R-flow-front/back、simbol 系列、red-parts-glow 和两侧 triangle 装饰层。
- AURA_54/AURA_55 等原始 SPR 帧虽已提取，但构建没有对应动态纹理播放。这些缺失的模型光效不应因 PCF 不可见而一起被搁置。

因此目前是局部能力探针/近似效果的部署，尚不是完整 idle 特效的还原。29 个节点不能简单按数量换算完成度，但缺失的左右光带恰好属于参考中很显眼的部分。

注意：目录里存在 `SIDE_ELEC` 模型不代表本 idle 组直接引用了它。应沿组内实际引用实现，不能仅按资源文件名选择一个“看起来像电光”的模型。

## 3. 已确认：恢复的数据没有驱动实际构建

`effects.json` 已保存颜色曲线 Ck、缩放曲线 Sk、挂点、朝向和重复规则，但模型构建脚本没有读取这个文件；实际仍为手工常量和固定层列表。

- `PARTS_BLUE` 使用固定缩放 0.15；该节点的原始 Sk 本来就是常量，缩放本身不是这层的已知错误。
- 原始 blue-parts 的颜色在蓝色区间变化；生成的 `fx_galilace_parts_blue.vmt` 没有对应颜色曲线，只用 Sine 改 `$alpha`。
- 主枪材质仍是静态蓝色 selfillum，没有颜色动画。眼部材质同样是固定 tint + Sine alpha。
- 没有播放原始 SPR 序列帧，因此“让亮度呼吸”不能表现原版光带内部的流动和纹理变化。

这也解释了为什么提取报告完整，却没有产生相应的游戏画面。数据恢复成功与运行时效果还原是两个阶段。

## 4. 已确认：眼部近似丢失了关键结构

原始 EYE 簇包括 main、CORE、rbw、prism 四层，其中 main/rbw 挂 `fix_effect_16`，CORE 挂 `fix_effect_15`；前三者的 Facing 为 CameraFacing，prism 为 ParentAlign。

当前 `build_galilace_vm.py:428` 的实现是：

- 两套固定的 XY/YZ/XZ 交叉面片，各 6 个三角形；
- 主层半边长 2.1、核心 0.9，均绑定 fx15；
- 人工向 X 方向偏移 0.55；
- 仅使用 SHINE_06 和 JY_SHINE_03 两种纹理，没有恢复 rbw/prism 层。

固定交叉面不能保持与相机相同的朝向，侧看会缩窄或露出面片；把不同挂点的层合并到 fx15，也改变了原始空间关系。扩大面片或增强颜色只能改变近似结果，不能补回这些结构。准确尺寸还需核对 FlareSprite 的尺寸语义，不能直接把 CF 的 max_scale 当 Source 半径。

## 5. 已确认：Blender 外观通过不能作为游戏外观通过

`effects/probes/blender_eye3.py:73` 将发光强度设为 4，`:142` 又叠加 `FOG_GLOW`。材质是 Blender 的 Emission/Transparent 混合，并非加载 Source VMT 后按同一 shader 渲染。

这类预览能辅助判断几何与位置，却额外创造了游戏材质未验证的发光和扩散效果。因此 `plan.md §7.5` 的“Blender 渲染验证位置/外观正确”，其中外观结论超出了证据范围。需要在目标游戏里做同位置、同材质的验证。

另外，“贴图平均 alpha 约 5%，所以 CF 一定靠增益补偿”也不是已证明的渲染公式：本次实测 SHINE_06 的全图 alpha 均值为 12.49/255，但最大值为 254/255。低均值包含大量透明边缘，不能单凭均值推定亮核强度或混合方程。已有 ×8 alpha、×1.5 RGB 应标记为人为近似。

## 6. PCF：配置有排查点，但尚未证明引擎不支持

本次将实际部署且与 pak hash 相同的 PCF，用本机 dmxconvert 解成 `packed_pcf_decoded.txt`，确认：

- 包含 `cf_tianxi_probe`、`cf_tianxi_eye` 及其 core 定义；DMX 能反序列化不等于各 operator 在游戏中正确执行。
- probe 有 `Position Within Sphere Random` 初始化器；eye 和 core 只有寿命、颜色、半径等初始化，缺少明确从控制点设置位置的初始化器。这是眼部粒子的直接排查点：挂点绑定与每颗粒子的位置写入需要分别核验。尚不能仅据静态文本断言它们实际出现在世界原点。
- QC 的创建事件在 draw 第 5 帧；没有配套停止事件或切枪/中断恢复方案。因此即使显示问题修复，生命周期仍未完成。
- 当前生成器与 QC 均在 draw 中包含 probe 和 eye 两个创建事件；仍需验证游戏里是否实际送达，不能只凭文件中的事件文本下结论。

公开的 [Valve Source SDK 2013 viewmodel 代码](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/c_baseviewmodel.cpp#L127) 会先将事件交给武器，再视返回值交给基类；[基类粒子事件处理](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/c_baseanimating.cpp#L3621) 还要解析挂接类型、查找挂点、创建效果。这说明“事件字符串已编译进 MDL”只完成了其中一环。该 SDK 不能作为本机 CS:GO Legacy 的运行时证明。

`plan.md §7.5` 中“viewmodel PCF 路线当前不可用”的技术结论应收窄为“本轮自定义 PCF 探针未显示，具体失败环节未定位”。已有骨骼原点错误是历史问题；它也不能单独解释修正后全部不可见的情况。

如恢复诊断，应使用对照矩阵定位，而不是继续叠加参数：同一原生效果在世界实体和 viewmodel 上分别测试；同一自定义效果也分别测试，再拆开验证事件送达、实际控制点位置及 renderer。此处仅提出诊断方法，本轮没有执行这些运行时试验。

## 7. 当前已排除：磁盘上漏打包或旧 addon

本次独立读取 VPK 目录、preload 字节与数据段，比较仓库 staging（A）、实际 MIGI addon（B）和 pak 条目（C）：

- 37/37 文件 A=B；
- 37/37 文件 B=C；
- 包内粒子 manifest 含 `!particles/cf_tianxi_galilar_p1.pcf`；
- 包内包括两份新增眼部 mesh VMT。

所以 `plan.md` 中“35/37，最后两个 VMT 尚未核验”的记录已经过时；当前磁盘产物不存在该缺口。核查详情见 `failure_audit_20260916.json`。这不追溯证明截图拍摄时的版本，也不证明运行中的游戏已重新加载这些文件。

## 8. 处理顺序建议

1. 建立 29 节点到实际输出的覆盖表，区分已实现、近似、未实现和运行时失败；先恢复参考图最显眼的左右流光模型及 SPR 帧播放。
2. 让原始曲线和挂点数据驱动构建，再校准 EYE 四层的朝向、尺寸和位置；减少未记录的手工常量。
3. 将 Blender 检查限定为几何辅助；颜色、混合和光晕在目标游戏确认。
4. 将 PCF 失败单独定位，先核对 eye/core 位置初始化和事件路径；显示后再完成停止/恢复规则。
5. 最后校准亮度与后处理。现在继续增亮一个小光点，不会补出尚未构建的枪身光带、装饰层或动态颜色。

## 9. 按用户澄清重新评估：原始 CF 特效转换能否走通

用户明确说明截图里的特效是上一 agent 卡住后用 Blender 手工制作的替代效果。因此手工效果可见，只能说明这种替代内容能显示，不能证明 CF 原始效果已成功转换。本节评估的是原始数据驱动的移植，而非继续美化该替代品。

### 判断

**原始模型层和序列帧光效具备明确的可实施路径，值得继续；仅靠现有证据，不能承诺在纯 MIGI 资源包条件下完整重现全部 29 节点及 CF 的最终渲染。** 卡住的 PCF 路径只覆盖其中一类效果，不构成放弃其余原始资源转换的理由。

本轮增加的只读核查：

- 14 个 LTBModel 节点对应的模型 dump 均存在；逐 mesh 检查顶点为有限数，UV 数量与顶点数量匹配。这里只证明基础几何数据可用，尚不证明坐标和动画正确。
- 左右流光使用的 PLANE_02_4/5，每个模型为 8 顶点、6 三角形；有原始 UV、socket、offset 和固定 Sk。它们不是必须用 PCF 才能实现的自由粒子。
- AURA_54 与 AURA_55 各 24 帧，48 张已解码贴图全部为 256×128，原始帧顺序已保存。
- SPR 头的第二个整数分别为 11 和 10；现有提取脚本将其标为未知并未导出。公开 [LithTech sprite loader](https://github.com/jsj2008/lithtech/blob/master/runtime/client/src/sprite.cpp) 把该字段读作帧率，并参与动画时长/帧索引计算。因此 11/10 fps 是有源码依据的初始映射值，CF 是否沿用整数毫秒取整等细节仍待对照。
- [Source 的动画纹理代理实现](https://github.com/ValveSoftware/source-sdk-2013/blob/master/src/game/client/baseanimatedtextureproxy.cpp) 会读取纹理帧数、按配置帧率更新材质帧索引。它为 SPR→多帧 VTF 的映射提供了实现依据；本机 Legacy 的最终显示仍须做一次原素材样例验收。

### 分层可行性

| 层 | 原始数据转换路径 | 判断 / 剩余门槛 |
|---|---|---|
| 原始光效模型 | 原 LTB 顶点/UV → SMD；按原 socket/offset/Sk 绑定 | 高可行性；逐类校准朝向、坐标和 RenderStyle，不复用任意手工位置 |
| 表面流光 | 原 SPR 帧及帧率 → 多帧 VTF；贴回原 LTB UV | 高可行性；需本机验证动画材质、混合与播放相位 |
| 颜色/透明度曲线 | 原 Ck/Sk → 目标材质或离线采样后的动画数据 | 固定循环可映射；动作重置、共享材质相位需另验，CF alpha 语义先明确 |
| Sprite/FlareSpriteFX | 原贴图、挂点、尺寸/角度参数 → Source 中对应的 sprite 渲染逻辑 | 有条件可行；固定交叉面片不能代替相机朝向、视角亮度及遮挡行为的验证 |
| ParticleSystem | 原发射/寿命/运动/颜色参数 → PCF 对应 operators | 数据可恢复，目标运行通路尚未通过；需要有效的世界/viewmodel 对照 |
| 整体发光观感 | 在已正确显示的原素材上校准混合、亮度和目标后处理 | 跨引擎需校准，不保证与 CF 每个像素相同 |

公开 [FlareSpriteFX 实现](https://github.com/jsj2008/lithtech/blob/master/NOLF2/ClientFxDLL/FlareSpriteFX.cpp) 会根据视角计算 alpha/scale，解释了为什么恢复一张贴图和一条 Sine 曲线仍不足以复现它。这是语义适配工作，不是再用 Blender 手绘一个新光团。

PCF 排查还需修正一个判断：仓库存在 `_test_pos.txt` 等带位置初始化的试验版本。当前部署 eye/core 缺少该初始化器只是现状，不能据此声称“补上必然解决”，也不能在没有各版本运行结果的情况下将之前全部失败归因于同一项。

### 能决定是否继续的最小验收

仅选择原 `L-flow-front` 节点：使用原 8 顶点模型、原 UV、原 AURA_54 的 24 帧、原 socket/offset/Sk 和有依据的帧率，转换成 Source 模型及动画材质。保留原文件到输出文件的对应关系，不加入手工造型/手绘光效，也不以 Blender 增辉预览代替游戏验收。

通过条件：游戏里该光带显示在对应枪身位置，能播放全部原始帧，随换弹/检视正确跟随，朝向与透明混合可解释。这个样例通过即可证明最重要的一条原资源转换链路成立；它不能代替后续 PCF 或全部 29 节点的验收。

若此样例失败，按几何、静态首帧材质、动画播放、坐标跟随逐项隔离。若 PCF 最终被证实无法通过纯资源包接入，则完整效果需要额外运行时能力或明确减少范围；不能再把手工替代品称为原始特效移植完成。
